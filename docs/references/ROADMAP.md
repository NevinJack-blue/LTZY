# LTZY 对标赶超路线图

> 基于 Neo API（28.7 万行 Go）与 Sub2API（111 万行 Go）的完整源码解析，对照 LTZY 现状（约 4800 行 Python）制定的融合与赶超路径。
> 详细分析见同目录 9 份专题报告。

## 一、三家定位对比

| 维度 | New API | Sub2API | **LTZY（现状）** |
|---|---|---|---|
| **核心价值** | 通用模型网关：一个 API 接 40+ 上游 | 订阅账号转 API：拼车共享额度 | 本机模型路由 + 用量账本 |
| **上游模型** | 静态渠道配置（30+ 适配器） | **账号池**（OAuth 订阅账号 + API Key） | 静态线路（`LTZY_UPSTREAMS`） |
| **协议面** | 14 种下游协议 × 4 种上游协议 | 4 种入站 × 4 种上游，含链式转换 | **仅 OpenAI 同构** |
| **计费深度** | 6 类倍率 + 表达式引擎 | Token 级 + 多重倍率链 | 每百万 token 固定单价 |
| **成本核算** | 渠道 `used_quota`（我方扣费） | **实际/账号/标准三口径** | 仅售价 |
| **权限** | 4 角色 + Casbin + scope + step-up | 2 角色 + 功能开关 + 路由守卫 | 2 角色（admin/user） |
| **部署** | 单机为主 | 多实例集群（outbox/leader lock） | 单机单进程 |
| **依赖** | Go + SQLite/MySQL/PG | Go + PG + Redis | **Python 标准库 + SQLite** |
| **前端** | React 19 + 70 路由 | Vue 3 + 60 路由 | **原生 JS（无构建）** |
| **代码量** | 28.7 万行 Go | 111 万行 Go | 0.48 万行 Python |

### 三家的本质差异

```
New API  = 「广度」：上游多、协议多、页面多、配置多
Sub2API  = 「深度」：账号资产化、调度智能化、成本精细化
LTZY     = 「轻」：零依赖、单文件、可审计、数据不出本机
```

**LTZY 不该在「广度」和「深度」上硬拼**——那是数十人年投入。应守住「轻」这个差异化，选择性吸收两家已被验证的**机制**（而非功能量）。

## 三、赶超策略：不打阵地战，打差异化

### 三条不打的仗（正视差距）

1. **上游覆盖广度**：40 个适配器是数年积累，且每个都要真实联调。LTZY 应**只做 5-8 家主流**（OpenAI、Anthropic、Gemini、DeepSeek、通义、Moonshot），做深而非做全。
2. **多实例集群**：outbox、leader lock、缓存广播——单机产品无此需求，硬做只会增加故障面。
3. **账号池拼车**：涉及 OAuth 逆向、指纹伪装、订阅条款风险。LTZY 定位「自有 API Key 中转」，不做订阅共享。

### 三条要打的仗（差异化优势）

#### 优势 1：零依赖单文件可审计

两家都需 Go 编译 + PG + Redis。LTZY 只需 `python server.py`。

**要做的是把「轻」做到极致**：
- 保持标准库零依赖（当前已做到）
- 单文件前端无构建（当前已做到）
- **加一条两家都没有的：数据全部留在本机，可 SQLite 直接打开审计**

#### 优势 2：成本透明（两家都有空位）

**这是最大的机会点。** New API 的分析明确写着：

> 现在只有 `channel.used_quota`（我方扣费）与 `channel.balance`（上游余额），**没有「上游真实成本 vs 我方售价」的毛利表**。

Sub2API 已经做了（三口径成本），但只在后台看板里。

**LTZY 可以做「每个请求都显示毛利」**：
- 给线路加 `cost_input_price` / `cost_output_price`（我方采购价）
- 已有 `input_price` / `output_price`（售价）
- 每笔 `receipt` 同时记 `cost`（售价）与 `upstream_cost`（成本）
- 前端小票直接显示「本次毛利」

这是两家都没做到「请求级毛利可见」的地方。

#### 优势 3：账单可复核的极致

New API 的 `LogOther` 三级可见性、Sub2API 的 4 段 cost 拆分，都值得吸收。LTZY 的定位是「账本」，应该把这个做到最强：

- 价格快照**不可变**（已有 `price` JSON）
- 增加**价格版本历史表**（两家都缺「价格变更时间线 + 历史计费复现」）
- 每笔请求可**按当时的价目复算**

## 五、必须遵守的门槛

### 许可

- **New API 是 AGPL-3.0**（含附加条款）。可学架构与交互，**不可复制代码**到 LTZY。若要复用代码需先做许可审查并接受 AGPL 传染。
- **Sub2API** 见其 `LICENSE`（需单独核对）。
- LTZY 当前无 LICENSE 文件 —— **发布协作前应先加一个**。

### 不可妥协的红线

1. **不抄代码，只学机制** —— 所有实现必须自己写
2. **不引入运行时依赖** —— 零依赖是 LTZY 的立身之本，Python 标准库足够实现上述 90%
3. **不承诺未验证的能力** —— 两家都有「P1+ 显示假入口」的问题，LTZY 应坚持「未上线不显示」

## 六、立即可以做的三件事

按「成本最低、价值最高、风险最小」排序：

1. **A1 易支付回调加固**（半天）
   - LTZY 的 `handle_pay_notify` 当前接收全部 query 参数参与验签，存在 Sub2API 注释里明确描述的「参数注入」风险面
   - 加白名单 + 值内分隔符检查 + pid 绑定，半天可完成并有测试

2. **A3 + A5 失败作用域与诊断**（一天）
   - 改动集中在 `gateway.py` 的 `Problem` 与 `chat()` 错误分支
   - 直接改善排障体验

3. **B1 + B2 成本/毛利双轨**（两天）
   - 数据库加两列 + 计费加一行 + 前端小票加一行
   - **这是两家都没做好的差异化卖点**

## 七、一句话结论

> 不要在「上游数量」和「集群规模」上追，那是以己之短攻彼之长。
> 要在「零依赖可审计」「请求级成本透明」「账单可复算」三件事上做到极致——这恰好是两家为了通用性而牺牲掉的地方。
